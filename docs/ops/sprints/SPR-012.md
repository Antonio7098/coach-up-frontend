# Sprint SPR-012 — Incremental Triage Agent Rollout

Implement the triage pipeline in small, testable increments that preserve current behavior at every step. Each stage runs end-to-end across Convex, Next API, and UI debug surfaces, with feature flags and mocks to ensure safe rollout.

Meta
- Sprint ID: SPR-012
- Status: in progress
- Start: 2025-09-09
- End: 2025-09-23
- Depends on: SPR-008 (Summary State Management)
- Related: SPR-010 (Triage Agent plan)

Goals
- Add triage metadata to interactions (assessmentType, triageProcessedAt, groupId unchanged) with zero-regression.
- Provide a mock triage that classifies and groups without external APIs.
- Integrate triage as a pre-summary step (best-effort, non-blocking) aligned with cadence.
- Ship an Observability panel to validate classifications and grouping in /coach-min.
- Gate provider usage behind flags; verify on staging before any production enablement.

Feature flags / env
- AI_TRIAGE_ENABLED=0|1: master flag (default 0)
- TRIAGE_PROVIDER=mock|google (default mock)
- TRIAGE_MODEL_ID=google/gemini-2.5-flash-lite (example)
- TRIAGE_TIMEOUT_MS=4000 (example)

Deliverables (incremental, shippable at each stage)

Stage 0 — Schema and surfacing (No behavior change)
- Backend (Convex)
  - Add fields to interactions: assessmentType (enum: single_qa_pair | roleplay_scenario | general_chatter | unknown), triageProcessedAt (number, ms). Add index by_session_assess_type_ts = ["sessionId", "assessmentType", "ts"].
  - No writes yet. Backfill: leave fields null.
- Next API
  - Include assessmentType, triageProcessedAt in /api/v1/interactions and /api/v1/transcripts payloads when present; otherwise omit/undefined.
- UI (/coach-min and /coach-debug)
  - In transcript/debug views, show badges for assessmentType when present; hidden if absent.
- Tests
  - Unit (Vitest): interactions mapping includes new keys when present.
  - E2E (Playwright, MOCK_CONVEX=1): no regressions in existing specs; new fields tolerant.
- Exit criteria
  - All current CI green, no behavior change; new fields visible only when populated.

Stage 1 — Mock triage (manual trigger, non-blocking)
- Backend (Convex)
  - mutation triage:setResults(updates: { messageId, assessmentType, groupId? }[]): validates enum; sets triageProcessedAt=now; idempotent.
  - action triage:runMockForSession(sessionId, limit=20): fetch last interactions by_session_ts; classify deterministically (e.g., if user→assistant pair within 2 turns => single_qa_pair; >2 user/assistant alternating => roleplay_scenario; else general_chatter). Calls setResults.
- Next API
  - /api/v1/triage?sessionId=... [POST]: if AI_TRIAGE_ENABLED=1, invokes Convex action triage:runMockForSession; returns { updated, tookMs }.
- UI (/coach-min)
  - New Debug tab: TRIAGE
    - Table of recent interactions (messageId, role, short text) with columns groupId, assessmentType, triageProcessedAt (relative time).
    - Buttons: [REFRESH], [RUN_TRIAGE_NOW] (visible only when AI_TRIAGE_ENABLED=1).
- Tests
  - Unit: enum validation; setResults idempotency; mock classifier cases.
  - E2E: run [RUN_TRIAGE_NOW] then verify badges populate in the panel.
- Exit criteria
  - Manual triage works via UI; no impact on summary cadence; feature-flagged.

Stage 2 — Pre-summary best-effort triage (cadence integration)
- Backend (Convex)
  - In functions/summaries.ensureJob (before reserving a new summary), call triage action with a short timeout (TRIAGE_TIMEOUT_MS). Swallow failures and proceed (logs include requestId, reason). Do not degrade cadence latency.
  - Optionally store a transient event row in events table: { kind: "triage_attempt", provider, ok, dtMs }.
- Next API
  - /api/v1/session-summary POST: Best-effort pre-call to /api/v1/triage added (short timeout, forward auth, failure-swallowed).
  - /api/v1/interactions POST (cadence path): Best-effort pre-call to /api/v1/triage added immediately before summary generation (short timeout, forward auth, failure-swallowed).
- UI
  - TRIAGE tab now auto-refreshes after assistant replies and during the short polling window, so triage results appear without manual refresh.
- Tests
  - Integration (Vitest): ensureJob path executes triage action at most once per due evaluation; does not block reservations on error.
  - UI unit/integration: verify auto-refresh calls occur after assistant reply and during poll loop.
- Exit criteria
  - Cadence p95 unchanged; triage metadata starts appearing automatically when due.

Stage 3 — AI API provider behind flags (staging only)
- AI API
  - POST /triage/batch (staging): input { sessionId, batchSize?, cutoffIndex?, messageIds?[] }; output list of { messageId, assessmentType, groupId? } with requestId, latency, tokens, provider, modelId. Note: messageIds reflect the exact slice since last summary cutoff to match the summary batch.
  - TriageClient base + Google provider; Mock provider as fallback.
- Convex action
  - triage:runForSession(sessionId, limit=20): route to provider (TRIAGE_PROVIDER). Fetch latest cutoffIndex and compute slice > cutoffIndex (bounded by limit). On success, call setResults; on failure, if TRIAGE_PROVIDER=google and fallback enabled, try mock.
- Next API
  - /api/v1/triage delegates to Convex action triage:runForSession.
- UI
  - TRIAGE tab shows provider + modelId in header (if available) and last status.
- Tests
  - Contract/API tests (against staging AI API) gated by env; sample transcripts validate grouping.
  - Costs/latency collected in logs; not used in prod yet.
- Exit criteria
  - Staging verification complete (accuracy > 85% target per SPR-010); no production enablement yet.

Stage 4 — Observability and SLOs
- Dashboards/Alerts
  - Add triage metrics to Prom: requests, errors, latency p95, classifications per type.
  - Alerts on error rate and timeouts.
- UI debug
  - Add quick filters by assessmentType and groupId; add counts per group in session.
- Load/Smoke
  - k6 smoke: ensure triage overhead keeps summary p95 < prior baseline; triage p95 < 5s.
- Exit criteria
  - SLOs met; triage can be considered for selective production enablement on a subset of traffic behind flags.

Out of scope for this sprint
- Real-time per-message triage.
- Production default enablement of external provider.
- Deep performance optimization beyond keeping under budget (future sprint).

Acceptance criteria
- Stage 0: New fields exist; no regressions; API payloads tolerant.
- Stage 1: Manual triage via UI populates assessmentType and triageProcessedAt; grouping supported where returned; tests green.
- Stage 2: When summaries.ensureJob deems due, a best-effort triage attempt runs without blocking; cadence p95 unchanged.
- Stage 3: Staging-only provider integration passes contracts and achieves accuracy target; flags default to mock/off.
- Stage 4: Metrics and alerts exist; debug UI enables quick validation; triage p95 < 5s for batch 20 in staging.

Risk & mitigations
- Provider latency/cost: hard timeout, flag default to mock, idempotency on updates, optional fallback-to-mock.
- Schema migration: optional fields; no data rewrite; roll-forward safe.
- Cadence slowdown: triage runs best-effort, never blocks reservation.

Rollback plan
- Set AI_TRIAGE_ENABLED=0 to disable all triage paths quickly.
- Keep TRIAGE_PROVIDER=mock to avoid external calls while preserving UI flows.
- Leave schema as-is (fields optional and unused when disabled).
